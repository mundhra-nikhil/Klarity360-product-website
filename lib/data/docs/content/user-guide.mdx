## **1\. Application Purpose**

Klarity 360 is a reconciliation and validation platform used to compare datasets between source and target systems — any JDBC-supported database (Oracle, SQL Server, PostgreSQL, MySQL, and others) and Microsoft Fabric. It is built for migration and transformation projects where teams need evidence that data landed in the target completely and accurately.

Users define validation processes through configurable table/column mappings, apply comparison rules with tolerance thresholds, execute row-level and rule-level validation, and generate reconciliation reports suitable for sign-off and audit. AI-assisted discovery reduces the manual effort of mapping large schemas.

## **2\. User Roles**

**QA User** — owns the technical workflow: configures connections, creates processes, defines mappings and rules, executes runs, investigates mismatches, and exports reports. On failure, the QA user determines whether the cause is a genuine data issue, a mapping error, or an over-strict rule.

**Business User** — consumes outcomes: reviews pass/fail results on the dashboard, checks reconciliation reports for business-critical fields, and receives emailed reports for sign-off. Does not create or modify processes.

## **3\. High-Level Application Flow**

The user signs in via Microsoft SSO and lands on the Dashboard. After ensuring the needed source and target connections exist, they create a process through a four-step wizard — connections, mapping, rules, run. The dashboard reflects live execution status, and on completion the user reviews results and downloads or emails the reconciliation report.

_Login → Dashboard → Connections → New Process (Steps 1–4) → Execution → Report & Analysis → Recon / Email Report_

## **4\. Login Flow**

The application offers a single option: **Login with Microsoft**. Clicking it redirects to Microsoft SSO, where organizational credentials are authenticated and access permissions validated — there is no local username/password fallback. On success the user lands on the Dashboard; on failure an error is shown and the user stays on the login page. Expired sessions redirect back to login for re-authentication.

## **5\. Dashboard**

The Dashboard is the operational landing page, showing validation health at a glance.

**KPI cards:** Total Processes, Rows Compared (cumulative records compared, indicating coverage), Total Rules, Rules Passed, and Rules Failed (rules whose latest run failed, signalling discrepancies to investigate).

**Recent Processes table:** one row per execution, with Process Name, Process Code, Status (Running/Passed/Failed), Last\_Run, Source–Target, Rules Failed, and Actions.

**Status logic:** a process is **Passed** when all rules pass, **Failed** when at least one critical rule fails. Criticality is set per rule during configuration; non-critical failures are reported but don't fail the run.

## **6\. Dashboard Actions**

Completed processes (Passed or Failed) share these actions: **View** (opens Report & Analysis — _not in current release_), **Copy** (duplicates the configuration), **Export Config**, **Recon Report**, **Email Report**, and **Delete** (with confirmation).

A **Passed** process additionally offers **Schedule & Run** (reopens at the execution step). A **Failed** process instead offers **Retry**, which re-runs the identical configuration and updates the dashboard on completion — and even failed runs keep their partial outputs and failure reports available for investigation. A **Running** process offers View, Refresh, Copy, and Export Config; Pause and Stop are planned but not in the current release, so a running execution cannot be interrupted.

## **7\. Connections Module**

Connections are reusable and selected by name inside processes. The application supports **any database with a JDBC driver** (Oracle, SQL Server, PostgreSQL, MySQL, etc.) and **Microsoft Fabric**.

**Create:** the user completes a form with Connection Name, Connection Type, credentials, and server/file details — the fields adapt to the type (a JDBC connection needs host, port, database/service name, and credentials; Fabric needs workspace and lakehouse details with the appropriate auth method).

**Validate: Test Connection** attempts a live connection. Success makes the connection selectable in processes; failure shows a details option with the underlying error so the user can correct and re-test.

**Delete:** blocked when the connection is referenced by any process — _“Connection is associated with one or more processes and cannot be deleted.”_ — preventing orphaned processes that would fail at runtime.

## **8\. New Process Creation**

**Step 1 — DB Connection.** Enter Process Name and Description, select Source and Target connections. Mandatory fields and connection accessibility are validated before Step 2, so mapping never starts against an unreachable database.

**Step 2 — Table & Column Mapping.** Two approaches: **Auto Discover with AI** inspects both schemas and suggests table pairs, mapping columns via names, metadata similarity, and structural matching; suggestions are reviewable — accept, adjust, or remove them, with unconfident matches left for manual handling. **Add Mapping Manually** lets the user pick source/target tables and map columns individually — the fallback for renamed or restructured schemas. Mandatory mappings and metadata availability are validated before Step 3.

**Step 3 — Comparison Rules.** Each rule has a name, description, tolerance options, and report options. Three rule types:

*   **Case Sensitivity** — whether “SMITH” vs “Smith” counts as a mismatch.
*   **Null Check** — flags values null on one side but populated on the other, catching silent data loss.
*   **Tolerance Validation** — numeric values may differ within a threshold, absorbing rounding/precision differences.

Output scope per rule: Missing records only, Value mismatches only, or All differences.

**Step 4 — Run Process.** Only **Manual Run** is supported currently. **Run Now** saves the configuration, creates an execution instance with a unique Process Code, and starts the validation engine.

## **9\. Process Execution**

An execution moves from **Running** to **Passed** or **Failed**, with the dashboard updating dynamically. The engine runs four sequential stages:

1.  **Schema Validation** — column presence, data types, structural compatibility; broken mappings fail fast before data is read.
2.  **Data Validation** — row-level comparison using the compare key columns, identifying missing records, duplicates, and value mismatches.
3.  **Rule Validation** — applies the configured business rules, recording pass/fail per rule.
4.  **Tolerance Validation** — reclassifies numeric differences within threshold as matches.

If a stage hits an unrecoverable error (e.g., a connection dropping mid-run), the execution is marked Failed and outputs generated so far are preserved.

## **10\. Report Generation & Analysis**

After execution, the system generates the recon report, per-rule analysis, mismatch output, and summary metrics.

**Report & Analysis page** _(not fully implemented)_ — will present rule outcomes, comparison statistics, and failed records in-app.

**Recon Report** downloads an Excel workbook with these sheets:

**Summary** — Process Code, Rule Name, Status (Match/Mismatch), Report Run Date, Rule Description, Database Type, Table Name, Field Count, Records Count, Matched Records, Mismatch Records, Match Accuracy (%), Value Differences, Top 5 Columns Cover (%), Missing Records, and Duplicate Records.

**Differences** — row-level mismatch detail: Compare Key Columns, Key Values, Mismatch Columns, Source and Target Values side by side, Mismatch Repeat Count, and Weightage % (contribution to the overall result). Repeated high-weightage patterns typically indicate systematic transformation issues rather than isolated errors.

**Missing (Source) / Missing (Target)** — records present in one dataset but absent from the other.

**Duplicate (Source) / Duplicate (Target)** — duplicates in each dataset; both sheets list Compare Key Columns, the duplicated Key Values, and the Repeated Count.

**Email Report** opens a popup for recipient addresses and a message body (subject line is pre-set) and sends the workbook as an attachment — the standard delivery path for Business users.

## **11\. Notifications & Error Handling**

Email notifications are sent on process completion, process failure, and report generation.

**Connection failure** — an error is shown and retry is allowed; a mid-execution drop marks the run Failed, after which the user can fix the connection and Retry from the dashboard. **Rule failure** — a critical rule failing marks the process Failed; this is an expected validation outcome, and failure reports remain available for investigation. **Report failure** — the user is notified so generation can be re-triggered rather than silently missing output.

## **12\. End-to-End Use Case**

A QA user validates a CUSTOMERS table migrated from Oracle to a Fabric Lakehouse. They create and test both connections, then build a process: Auto Discover maps the table and columns, a Null Check is set on customer ID and email, and a Tolerance rule absorbs rounding on account balance. The run fails — emails populated in Oracle are null in Fabric. The Differences sheet pinpoints the affected keys; after the migration team fixes the load, Retry passes and the report is emailed to the Business user for sign-off.

## **13\. Summary**

Klarity 360 covers the full migration-validation lifecycle — connection management, AI-assisted mapping, rule-based comparison, execution monitoring, and audit-ready reconciliation reporting — giving QA users row- and rule-level diagnostics and Business users clear, shareable pass/fail outcomes.
